HR to Okta Integration - Troubleshooting Guide

← Back to index

Overview

This guide describes common errors that can occur when the HR to Okta Integration runs. It explains the possible causes of each error and provides steps to diagnose and resolve the issue.

Troubleshooting

This section covers the errors and the corresponding solutions.

Error: Creation validation failed. No matching user was found using the configured correlation attribute.

After the Aquera integration submitted a request to create the user in Okta, it could not locate the user. Aquera validates the operation by searching Okta for the newly created user using the configured correlation attribute (Source Match Expression). The validation fails when no matching user is found. Either Okta did not create the user, or it created the user without a value in the correlation attribute.

Solution

Perform the following steps to identify and resolve the issue:

  1. Verify that the following settings are configured in the integration:
    • Make sure that the Source Match Expression is configured.
    • Make sure that the attributes used in the Source Match Expression are mapped to the corresponding attributes in the Attribute Map.
  2. Verify that the following settings are configured in the Okta application:
    1. Configure the Account Reconciliation settings by performing the following steps:
      1. Navigate to Applications and Resources > Applications. Search and select the Custom Identity Source application.
      2. Navigate to Provisioning > To Okta > Account Reconciliation. Click Edit and configure the following fields:
        • Confirm new users: Select the Auto-confirm new users checkbox.
        • Imported users is an exact match to Okta users if: Select the The following attribute matches: option and select the attribute used to match imported users with existing Okta users.
        • Confirm new users: Select the Auto-confirm exact matches checkbox.
      3. Click Save.
    2. Configure the attribute mappings using one of the following methods:
      • Navigate to Directory> Profile Editor, open the app and click Mappings> Configure User mappings. Make sure that the attributes used in the Source Match Expression are mapped.
      • If the above option is unavailable, enable the Auto-Create and Map Attribute in Okta Application toggle in the Attribute Map section of the integration and make sure that the required attributes are mapped.

      • Alternatively, manually map the attributes in Okta and set Apply mapping on user create and update. If an attribute does not exist, click Add Attribute to add it.

      • After completing any one of the above methods, open the application in Okta. Navigate to Provisioning > To Okta > Okta Attribute Mappings and verify that the required attributes are listed with Create and Update in the Apply on column. If an attribute is not listed, click Show Unmapped Attributes and click Force Sync.

    3. Review imported users and verify the import status by performing the following steps:
      1. Open the application and navigate to Import tab, check wether the users is listed under imported users need review. If the user is waiting for review then perform the following steps:
        1. Select the user and click Confirm Assignments. Ensure that you have completed step a before proceeding.
        2. Navigate to Reports > Import Monitoring. Check the Status.
        3. If the status is Completed, the import is successful. If the import fails, click View in the Logs column, resolve the error, and run the integration again.
    4. Configure the profile source priority at the application or attribute level section by performing the following steps:
      1. Select the Custom Identity Source Application, navigate to Provisioning> To Okta> Profile & Lifecycle Sourcing and enable Allow Custom Identity Source to source Okta users checkbox.
      2. At the application level, navigate to Directory> Profile Sources and check whether another application has a higher priority than the application you created in Okta.
      3. At the attribute level, navigate to Directory> Profile Editor and select User(default). Under Attribute section, select the Base section and click the info icon of the correlation attribute.
      4. In the Source priority section select Inherit from Okta or Override profile source option.
      5. If another source controls the user or correlation attribute perform the following steps:
        1. Confirm with the customer which application should manage and update the correlation attribute in Okta.
        2. At the application level, navigate to Directory > Profile Sources and set the required priority for the Custom Identity Source application.
        3. At the attribute level, select Override profile source from the Source priority drop-down menu, select the custom identity source application from the Add Source drop-down menu, and click Save Attribute.

    5. Search for the user using the correlation attribute and take the required action based on the result:

      • Navigate to Directory> People and click Advanced search. 
      • Select the correlation attribute, enter the required value, and click Search. If the user is found, open the user profile and navigate to the Profile tab. Based on the search result, perform the following actions:
        • User not found in Okta: The user was not created. Recheck steps (a) and (c).
        • User exists, but the correlation attribute is empty: The attribute value is not being mapped. Recheck steps (a) and (b), and clean up the user has described in step 3before running the integration again.
        • User exists with a different value: Compare the value with the source record. Correct the source data or mapping expression to ensure that both values match.
  3. If a user is created in Okta without the correlation attribute, Aquera may create a duplicate user during the next integration run. To avoid this, perform either of the following options before running the integration again:
    • Update the correlation attribute on the existing Okta user:
      1. Navigate to Directory> People and open the user profile.
      2. Check whether Profile sourced by Custom Identity Source is displayed below the user's name and whether the custom identity source application is listed under Assigned Applications.
      3. Click More Actions and select Disconnect from Custom Identity Source and click confirm.

      4. Navigate to the Profile tab and click Edit. Enter the correlation attribute value from the source record and save the changes.

    • Delete the user from Okta:

      1. Navigate to Directory> People and open the user profile.

      2. Click More Actions and select Deactivate, click Delete and click confirm.
        Note: Use this option only for users created during the failed integration run who are not yet in use. Deleting a user removes their application assignments, group memberships, and history.

  4. After fixing the issue, perform the following steps:

    • Run the integration again and verify that the error is resolved.Confirm that only one Okta user exists with the correct correlation attribute.

    • For users who were disconnected using option (a) in step 3, verify that Profile sourced by Custom Identity Source is displayed again below the user's name.

Error: Creation failure: 409, detail= Creation validation failed. Multiple matching users were found: <users>

After the Aquera integration submitted a request to create the user in Okta, it could not locate the user. Aquera validates the operation by searching Okta for the user using the configured correlation attribute (Source Match Expression). The validation fails when it founds more than one user in Okta with the same correlation value. The integration cannot identify which is the right user.

Causes for this error:

  • A duplicate user was created, or the user is created manually in the Okta.
  • When the Source Match Expression field uses an attribute with no unique value, or same value has been configured to different users.

Solution

Perform the following steps to identify and resolve the issue:

  1. Identifying the duplicate records by performing the following steps:
    1. Copy the usernames listed in the error. 
    2. Log in to your Okta instance.
    3. Navigate to Directory> People and click Advanced search.
    4. Select the target attribute configured in the Source Match Expression, select Equals, enter the required value, and click Search. The users listed in the error message are displayed. Check the status of each user.
    5. Open each user profile, check whether Profile sourced by Custom Identity Source is displayed below the user's name and whether the Custom Identity application is listed under Assigned Applications.
    6. Click Profile tab and compare the values with the source record.
  2. Decide which user record to keep
    • Keep the user record which is managed by Custom Identity Source application and matches the source record.
    • If it is unclear which user record is correct, confirm with the customer which record to keep before making any changes.

  3. Perform one of the following actions for the duplicate user record:

    1. Delete the duplicate user record by performing the following steps:
      1. Select the user profile you want to delete.
      2. Click More Actions and select Deactivate.
      3. Click Delete and click confirm.

    2. Correct the correlation attribute value:

      • If the source data is wrong in the source system correct the values.
      • If the value is wrong in the Okta, perform he following steps to correct it:
        1. Select the user profile you want to update.
        2. If Profile sourced by Custom Identity Source is displayed below the user's name, click More Actions and select Disconect from Custom Identity Source.
        3. Navigate to Profile tab and click Edit. Change the correlation attribute.
        4. Click Save.
  4. Verify the Source Match Expression in Aquera integration:
    1. Navigate to Connections section under Configuration tab.

    2. Configure the Source Match Expression using an attribute with a unique value and click Save. Note: Make sure that the attributes used in the Source Match Expression are mapped to the corresponding attributes in the Attribute Map and Okta profile mapping, as described in the troubleshooting steps for Creation Validation Failed error.

  5. Prevent duplicate correlation attribute values in Okta by performing the following steps:
    Note: This procedure applies only if the correlation attribute is a Custom attributes. If the correlation attribute is a Base attribute, skip this section.

    1. Navigate to Directory > Profile Editor. The Profile Editor page is displayed.
    2. Select User(default) profile.
    3. Click Custom under Filters in the Attribute section.
    4. Click the edit icon of the correlation attribute.
    5. Select the Value must be unique for each user checkbox in the Restriction field.
    6. Click Save Attribute. Okta will prevent users from having the same value for this attribute.
  6. After fixing the issue, run the integration again and verify that the error is resolved.

Error: creation failure: code= 400, detail= Creation validation failed. User created, these attributes were not updated: <list>.

 After Aquera creates a user in Okta, it reads the user profile and compares the attribute values stored in Okta with the values sent by Aquera. The validation fails when one or more attributes have different values.

Causes for this error:

  • The attribute is not mapped in the Aquera Attribute Map or does not exist in the Okta application user profile.
  • The attribute is not mapped correctly in the Okta application-to-Okta user profile mapping, or the mapping expression changes the value.
  • Another application has a higher profile source priority and controls the user profile or attribute value.
  • The attribute value sent by Aquera does not match the data type or format expected by Okta.

Solution

Perform the following steps to identify and resolve the issue:

  1. Compare the values in the Okta application by performing the following:
    1. Note the attributes that are listed in the error.
    2. Navigate to Directory > People.
    3. Open the user profile and navigate to Profile tab. Check whether the attributes listed in the error have empty values or values that differ from the expected values.
      • If the value is empty then the attribute is not mapped in the attribute mapper. In this case refer to steps 2 - 4.
      • If a different value is present then refer to steps 4 - 6.
  2. Verify in Aquera wether the attribute is mapped in the attribute mapper by performing the following steps:
    1. Navigate to Mapping and Assignments > Attribute Map in the Aquera integration.
    2. Check wether all the listed source attribute are mapped to its corresponding target attribute.
    3. In the Enter objects for preview field enter the user ID to preview the values the integration will send to Okta. If the values are incorrect correct the source expression or the target attribute and save it.
  3. Verify wether the attribute exist in the Okta application by performing the following steps:
    1. Navigate to Directory > Profile Editor in the Okta application.
    2. Search for the application and open it.
    3. Check wether the Attributes section contains all the attributes that was listed in the error. If the attributes are missing then perform any one of the action:
      1. Enable the Auto-Create and Map Attributes in Okta Application toggle in the Aquera integration and click the refresh icon next to the target application. The integration creates the missing attributes in the Okta application and maps them to the Okta directory attributes.
      2. Click +Add Attribute on the application user profile that you have selected and add the attribute with the same name and data type as the Okta directory attribute.
  4. Verify the attribute mapper between the Okta application to Okta by performing the following steps:
    1. On the app user profile click Mappings and select Configure User mappings for the application you have selected in step 3.
    2. In the <App name> to Okta User tab, check the listed attribute:
      • If the row shows Choose an attribute or enter an expression... it means the attribute is unmapped and the user is created without value.
      • If the mapping is active it is indicated by a green arrow, click the arrow and select Apply mapping on user create and update to ensure that subsequent updates are reflected in the Okta user profile.
      • Make sure that the Okta profile mapping does not modify the attribute value using expressions such as toUpperCase() or substring(). If a transformation is required, configure it in the Aquera Attribute Map and map the attribute directly in Okta.

      • Aquera sends array attribute values to Okta as comma-separated text, and Okta must convert those values back into an array using a mapping expression in the attribute mapper.

        (appuser.numberArray != "" && appuser.numberArray != null) ? Arrays.flatten(appuser.numberArray) : {}
    3. Manually map the attributes and set the arrow to Apply mapping on use create and update, and click Save Mappings.
    4. Open the Custom Identity Source application and navigate to Provisioning > To Okta > Okta Attribute Mappings. Verify that Create and update is displayed in the Apply on column for each required attribute. Click Force Sync.
  5. Verify that this application controls the user profile by performing the following:
    1. Open each user profile, check whether Profile sourced by Custom Identity Source is displayed below the user's name and whether the Custom Identity application is listed under Assigned Applications.
    2. Navigate to Provisioning> To Okta > Profile & Lifecycle Sourcing.
    3. Check wether the Allow Custom Identity Source to source Okta user checkbox is selected. If not selected, select it.
    4. Navigate to Directory > Profile Sources and check the source priority If the user is assigned to multiple profile sources. If another application has a higher priority than the Custom Identity Source application, its profile values may take precedence.
    5. Navigate to Directory > Profile Editor > User(default) and click the info icon of each listed attributes.
    6. Select Inherit from Okta or Override profile source based on your requirements in the Source priority field. If you select Override profile source, ensure that the Custom Identity Source application has the required priority.

    7. Compare the attribute values sent by Aquera (refer to the preview in step 2) with the corresponding attribute data types configured in the Okta Profile Editor. Verify that the attribute values meet the following data type requirements:

      1. Number, Integer, or Boolean: Ensure that the values match the required data type. 
        For example: "12 hrs" is not a valid number.
      2. Enumerated values: Ensure that the values match one of the allowed values configured in Okta.
      3. Arrays: Values containing commas may be split into multiple elements in Okta. Aquera does not send multi-valued attributes containing objects. In such cases, the run report displays the message complex multi-valued attribute, not sent to Okta.
      4. If the values do not match the required format: Update the expression in the Aquera Attribute Map to send values in the format expected by Okta.
  6. Navigate to Reports > Import Monitoring and check the Status of the application.
    1. If the status is Completed, the import is successful. If the import fails, click View in the Logs column, resolve the error, and run the integration again.
    2. After fixing the issue, re-run the integration and verify that the error no longer appears in the run report and that the user's Profile tab in Okta displays the expected attribute values.

  • The attribute is not mapped correctly in the Okta profile mapping, or the mapping expression changes its value.
  • Another application has a higher profile source priority and controls the user profile or attribute value.

      1. Navigate to Provisioning> To Okta > Profile & Lifecycle Sourcing.

Error: update failure: code= 404, detail= Update validation failed. The user was not found.

After Aquera submits a request to update a user in Okta, it searches for the user using the Okta user ID to confirm the update. The validation fails when Okta cannot find a user with that ID. The user existed when Aquera loaded the Okta users at the beginning of the integration run but was deleted before the update could be confirmed.

Causes for this error:

  • The user was deleted manually or by another process in Okta during the integration run.
  • The user was deleted and recreated in Okta during the integration run, resulting in a new Okta user ID.

Solution

Perform the following steps to identify and resolve the issue:

  1. Check wether the user exists in the Okta application by performing the following steps:
    1. Log in to your Okta instance.
    2. Navigate to Directory > People. The People page is displayed.
    3. Click Advance search, select the correlation attribute, enter the required value, and click Search. You can also search using the username or email attribute.
      • User not found: The user may have been deleted. Proceed to step b.
      • User found with a new Okta user ID: The user may have been deleted and recreated. Proceed to step c.

  2. Identify who deleted the user and take the required action by performing the following steps:

    1. Navigate to Reports > System Log. The System Log page is displayed.
    2. Set the From and To to the start and end times of the integration run, and search for the username with the event type user.lifecycle.delete.initiated.

    3. Check the Actor column to identify who or what initiated the deletion. Take the required action:

      • If the user was deleted by mistake, confirm with the customer how to proceed, as permanently deleted Okta users cannot be restored.

      • If another application or process deleted the user, ask the customer to stop it from deleting users managed by the integration.

      • If the user needs to be created again, run the integration after resolving the deletion issue.

  3. If the user record was deleted and recreated then perform the following:
    • Re-run the integration. The next run creates the current user and updates it.

    • If more than one user is found with the same correlation attribute value, refer to the Creation failure: 409 error.

  4. After fixing the issue, run the integration again and verify that the error is resolved and that the expected attribute values are displayed in the user's Profile tab.

Error: deactivation failure, code 400, detail= Deactivation validation failed. <user> is still active.

After Aquera submits a request to deactivate a user in Okta through the Custom Identity Source application, it checks the user's status in Okta to confirm the deactivation. The validation fails when the user's status does not match the configured Okta User Deactivation Status and the user with any other status is treated as still active in Okta. 

Okta User Deactivation Status is an hidden attribute and by default it is set to DEPROVISIONED, which corresponds to the Deactivated status in Okta. If the user is Suspended or has any other status, the user is considered has active in Okta and Aquera reports an error.

Solution

Perform the following steps to identify and resolve the issue:

  1. Check the users status in Okta application perform the following steps:
    1. Log in to Okta instance.
    2. Navigate to Directory > People. The People page is displayed.
    3. Click Advance search, select the correlation attribute, enter the required value, and click Search, or you can search for the user with their name.
    4. Click the user profile and check:
      1. The status of the user.
      2. If Profile sourced by Custom Identity Source is displayed below the user's name.

  2. Identify the applicable cause and perform the corresponding troubleshooting steps:

    • Cause 1: The Custom Identity Source application does not deactivate the Okta user. Perform the following steps to resolve the issue:
      1. Log in to your Okta instance and select the Custom Identity Source application.
      2. Navigate to Provisioning > To Okta > Profile & Lifecycle Sourcing.
      3. Under When a user is deactivated in the app, verify that the selected option matches the Okta User Deactivation Status configured in the Aquera integration.
      4. If the settings do not match, confirm with the customer how inactive users should be handled in Okta and configure the appropriate option:
        • Deactivate: Click Edit, select Deactivate, and click Save. Ensure that Okta User Deactivation Status is set to Deactivate in Aquera.
        • Suspend: Click Edit, select Suspend, and click Save. Set Okta User Deactivation Status to Suspended in Aquera.
        • Do nothing: This option leaves the user active and may cause deactivation validation to fail.
      5. Re-run the integration and verify that the user's status in Okta matches the configured deactivation status.
    • Cause 2: Another application has higher profile source priority than the Custom Identity Source Application. Perform the following steps to identify and resolve the issue:
      1. Open the user's profile and check whether Profile sourced by Custom Identity Source is displayed below the user's name or whether another profile source is displayed.
      2. Navigate to Directory > Profile Sources. If another application assigned to the user has a higher priority than the Custom Identity Source application, that application controls the user's lifecycle.
      3. Determine which application should control the user's lifecycle. Based on your requirements, either change the profile source priority or deactivate the user through the application that controls the user's lifecycle.
    • Cause 3: Another Process Reactivated the User. Perform the following steps to identify and resolve the issue:
      1. Navigate to Reports > System Log and search for the user.
      2. Check whether an activation or reactivation event occurred after the user was deactivated. The Actor field displays who or what reactivated the user.
      3. If another process reactivated the user, ensure that the process does not reactivate users managed by the Aquera integration.
  3. Re-run the integration and verify that the error no longer appears in the run report and that the user's status in Okta is Deactivated.

Error: Access denied: Okta XaaS isn't enabled for your account. Please contact Okta Support.

Before uploading user records to Okta, Aquera sends a request to retrieve the open import sessions of the Custom Identity Source application. The request fails when Okta returns a 403 Forbidden error, indicating that access to the requested resource is denied. As a result, the integration stops without uploading any user records.

Solution

The following are the possible causes of the issue. Check the applicable cause and perform the corresponding troubleshooting steps.

  • Cause 1: API integration is not enabled in the Custom Identity Source application. Perform the following steps to verify and enable API integration:
    1. Log in to your Okta instance.
    2. Navigate to Applications and Resources > Applications.
    3. Search and select the Custom Identity Source application.
    4. Navigate to the Provisioning tab. If it shows Provisioning is not enabled, this is the cause.
    5. Click Configure API integration, select EnableAPI integration checkbox, and click Save.

  • Cause 2: Incorrect Identity Source ID configured in Aquera.

    1. Open the Custom Identity Source Application in Okta instance copy the application instance ID displayed in the URL after /identity_source/instance/.
      For example, in .../identity_source/instance/0oa14nx6m7jlzETYI1d8/, the ID is 0oa14nx6m7jlzETYI1d8.

    2. Compare the copied ID with the ID configured in the Okta connector used by the integration.
    3. Update the ID in the Okta connector  if the IDs do not match and click Save Changes.
  • Cause 3: The credentials used by Aquera do not have the required roles:
  • Cause 4: The Identity Source Application (XaaS) feature is not enabled:
    • If none of the previous causes apply and the integration continues to fail, contact Okta Support to request that the Identity Source Apps (XaaS) feature be enabled for your Okta organization. Provide the Okta organization URL and the Custom Identity Source application name and ID.
  • Re-run the integration and verify that the error no longer appears in the run report. Navigate to Reports > Import Monitoring and verify that the import status for the Custom Identity Source application is Completed.

Error: The Okta import process returned an error. Please review the Okta UI and the identity source session details.

After Aquera uploads user records to Okta through the Custom Identity Source application, it requests Okta to process the import session. The import fails when Okta encounters an error while creating, updating, or deleting the records and sets the import session status to error. As a result, Aquera stops the integration run.

Solution

Perform the following steps to identify and resolve the issue:

  1. Log in to your Okta instance.
  2. Navigate to Reports > Import Monitoring or click Monitor Imports displayed below the user's name in your Custom Identity Source application.
  3. Search your application at the time it run. It shows the Status has Failed.
  4. Click the arrow next to the record to expand it. When the import fails, a red Import failed card is displayed which shows the reason for the import failure.
  5. Click View in the Logs column. The System log page is displayed.
  6. If the Import failed card indicates that required permissions are missing, enable the missing permissions and re-run the integration. 
    Note: If it fails again contact the Okta support team, and provide the Custom Identity Source application name and ID, the time of the failed import, the error message displayed in the Import failed card, and the relevant log events.
  7. After fixing the issue, run the integration again and verify that the error is resolved and check the status of the record in the Import Monitoring page. Expand the report to know the details of users scanned, new, updated, unchanged or removed in the Import finished card.

Error: <operation>: import session timed out after <n> polling attempts <operation> 

After Aquera starts an import session in Okta, it checks the import session status to confirm that the import is completed. The validation fails when Okta does not complete the import within the expected time. Aquera checks the status up to 50 times over approximately 7 hours. If the import is still not completed, Aquera stops waiting and ends the integration run with an error.

Solution

Perform the following steps to identify and resolve the issue:

  1. Check the import status of the record by performing the followng steps:
    1. Log in to your Okta instance.
    2. Navigate to Reports > Import Monitoring, or click Monitor Imports displayed below the user's name in your Custom Identity Source application. The Import Monitoring page is displayed.
    3. Search for your application using the time of the integration run and check whether the status is In Progress, Completed, or Failed. Check if any other application ran around the same time.
    4. If the Status is Failed, click the arrow next to the record to expand it. A red Import failed card is displayed which shows the reason for the import failure. Follow The Okta import process returned an error troubleshooting error.
  2. If the import is queued behind other imports, perform the following steps:
    • In Import Monitoring, check whether other imports for the same Custom Identity Source application are running or queued at the same time.
    • Check whether another Aquera integration, Okta Workflow, script, or manual import is using the same Custom Identity Source application.
    • Schedule the imports to avoid overlapping integration runs, or use separate Custom Identity Source applications for different processes.
    • Wait for the import to complete before running the integration again.
  3. If a previous import is halted, perform the following steps:
    1. In Import Monitoring, check whether any previous import for the Custom Identity Source application is halted. For example, because the Import Safeguard threshold was reached.
    2. Click View in the Logs column to identify the reason.
    3. Review the halted import with the customer and take the required action:
      1. If the changes are expected, allow the import to continue in Okta.
      2. If the changes are not expected, cancel the import and correct the source data.
      3. If the Import Safeguard threshold needs to be changed, confirm the new threshold with the customer and update it in Okta.
    4. After the halted import is resolved and the queued imports are completed, run the integration again.
  4. If the import contains a large number of users, perform the following steps:
    1. In Import Monitoring, check whether the import was completed after the integration run timed out and whether any other imports were running at the same time.
    2. Check the integration run report to verify whether a large number of users were uploaded.
    3. If the import is completed, run the integration again to validate the results.
    4. For future bulk imports, schedule the integration when no other imports are running for the same Custom Identity Source application.
  5. If Okta is experiencing processing delays, perform the following steps:
    1. In Import Monitoring, check whether the import remains In Progress for several hours without other imports running.
    2. Check Status for any reported incidents.
    3. If an incident is reported, wait until it is resolved and the import is completed before running the integration again.
    4. If the import remains in progress, ask the customer to contact Okta Support with the Custom Identity Source application name, application ID, and import time.
  6. After fixing the issue, perform the following steps:
    1. Run the integration again after the previous import is no longer in progress.
    2. Navigate to Reports > Import Monitoring and verify that the import status is Completed.
    3. Click the arrow next to the import record to expand it. The Import finished section displays the number of users scanned, created, updated, unchanged, and removed.
    4. Verify that the integration run no longer reports the error.
