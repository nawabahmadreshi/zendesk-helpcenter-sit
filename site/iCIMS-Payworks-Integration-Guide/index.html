Overview

The Aquera platform enables your organization to scale complex data management by automating data integration across various resource types. Aquera's integrations facilitate automatic provisioning, ensuring consistency across systems. It enables organizations to streamline processes, dynamically scale resources, and automate repetitive tasks, ultimately enhancing efficiency in managing complex IT infrastructures and applications.

The iCIMS / Payworks integration synchronizes employees between iCIMS and Payworks. For each integration run, employees are synchronized in only one direction, based on the Sync Direction setting in the Parameters section. The integration does not synchronize employees in both directions during the same integration execution.

The following synchronization directions are available:

  • iCIMS to Payworks: It synchronizes employee lifecycle events from iCIMS to Payworks.
    When a candidate reaches a hire status in iCIMS, the integration creates the employee in Payworks. If the candidate is already matched to an existing Payworks employee, the integration updates only the fields whose values differ from iCIMS. Fields that already contain the same values are skipped. When a candidate reaches a termination status in iCIMS, the integration updates the employee's payroll status and termination date in Payworks.
    Note: This direction is triggered by the iCIMS webhook and processes one candidate for each event.
  • Payworks to iCIMS: It synchronizes organization and employment data from Payworks to the matching iCIMS People profile.
    If the matching iCIMS profile does not contain existing values, the integration performs an initial synchronization and writes the Payworks data to iCIMS. If values already exist, the integration updates only the fields whose values differ from Payworks. For terminated employees, the integration updates the configured termination status field in iCIMS instead of performing the standard employee data synchronization.
    This direction can be executed manually for a specific employee or scheduled to retrieve the full Payworks employee data. During a scheduled execution, each Payworks employee is matched to the corresponding iCIMS profile using the configured matching field.

Each synchronization direction has its own lifecycle operations, conditions, limits, and correlation settings. To match records between the two applications, the integration compares the configured iCIMS correlation field with the employeeNumber field in Payworks.

Key Functions - To be checked later

  • Creates, updates, and terminates Payworks employees from iCIMS hire and termination workflow events, driven by an iCIMS webhook.
  • Writes Payworks organization and employment fields back onto the matching iCIMS People profile, either for one named person or across the full Payworks roster on a schedule.
  • Correlates candidates between the two systems using a configurable iCIMS field matched against the Payworks employee number.
  • Applies independent lifecycle operations (Create, Update, Delete), conditions, and limits for each sync direction.
  • Supports a report-only mode that simulates every operation without writing changes.
  • Supports manual, on-demand runs for a single candidate or a single Payworks-correlated person, for testing.
  • Masks personally identifiable information (social insurance number, birth date, full tax setup) in logs, reports, and notification attachments.
  • Generates a per-record CSV report, run logs, a Log Insights (OpenSearch) dashboard, and success/failure email notifications.

Prerequisites

The following are the required setup steps before configuring this integration:

  • Tenant Account in the Aquera Admin Portal: You must have a tenant account with admin access in the Aquera Admin portal. Visit https://admin.aquera.io and register to get a tenant account. Contact your Aquera account manager to get Aquera tenant access.
    Note: If your organization is in the EU region, use the following URL to register: https://admin.eu.aquera.io/.
  • Configure Application Connectors in the Aquera Admin Portal: You need to configure the following application connectors in the Aquera Admin portal:
    • iCIMS: You must have an iCIMS connector configured in the Aquera Admin portal, with webhook access for the WorkFlowStatusChangeEvent event type. Refer to the iCIMS Configuration Guide for configuration details. - Validate
    • Payworks: You must have a Payworks connector configured in the Aquera Admin portal. Refer to the Payworks Configuration Guide for configuration details.

Integration Setup

This section details the configuration and mapping process required for this integration. It outlines the steps to create the integration and set up integration preferences.

Create Integration

Perform the following steps to create the integration:

  1. Log in to the Aquera Admin portal.
  2. Navigate to Integrations from the left side panel.
  3. Click Create Integration.
  4. Search for iCIMS / Payworks in the search box next to the Explore Templates section, and then select it to create a new integration.
  5. Enter a name and a description for the integration.
  6. Select your iCIMS and Payworks connector instances.
  7. Click Continue. The Overview tab is displayed for further configuration.

iCIMS Settings / iCIMS settings

This section allows you to configure how iCIMS candidates are matched to Payworks employees and how webhook events are identified as hire or termination events. The following fields are available for configuration:

  • Source Correlation Key / iCIMS correlation attribute: Select the iCIMS People field that stores the Payworks employee number used to match a candidate with the corresponding Payworks employee. The integration also writes the Payworks employee number to this field after creating an employee.
    Note: This field should use the same value as the corresponding correlation field configured for the Payworks to iCIMS direction. If different fields are configured, the two synchronization directions might not match the same employee records. The default value is External ID.
  • Hire Status Categories / Hire status categories: Enter the iCIMS workflow status categories that identify a candidate as ready to be created or updated in Payworks. Matching is not case-sensitive and ignores leading or trailing spaces.
  • Terminate Status Categories / Termination status categories: Enter the iCIMS workflow status categories that identify a candidate as ready to be terminated in Payworks. Matching is not case-sensitive and ignores leading or trailing spaces.
  • Hire Status IDs / Hire status IDs: Enter the workflow status IDs that identify a hire event. When configured, these IDs are used instead of Hire status categories to determine whether an incoming webhook event is a hire event.
  • Terminate Status IDs / Termination status IDs: Enter the workflow status IDs that identify a termination event. When configured, these IDs are used instead of Termination status categories to determine whether an incoming webhook event is a termination event.
  • Webhook Event Types / Webhook event types: Enter the iCIMS webhook event types that the integration should process as candidate lifecycle events. If the webhook payload does not contain one of the configured event types, or if no payload is received, the integration does not process a candidate and reports the execution as no action.

Payworks Settings / Payworks settings

This section allows you to configure the Payworks field used to match an employee with the corresponding iCIMS candidate.

The Payworks employee ID is an internal identifier used for API requests and is not written back to iCIMS. Advance Settings

PII & Security

  • Mask Sensitive Fields: Masks sensitive values in every log line, the CSV report, and the notification attachment. The forward payload carries the social insurance number, birth date, and the full Canadian tax setup, so this should stay enabled outside of a controlled debugging session.
  • Masked Field Names: Field names masked wherever they appear, matched case-insensitively against both the attribute name and the report column. A masked value is rendered as its last two characters only.

Settings

  • Transient Retry Attempts: How many times a call is retried after a transient failure (429, 502, 503, timeout) before the record is reported as failed. Retries back off exponentially. Set to 0 to disable. Default: 3.
  • Retry Backoff (ms): Base delay before the first retry. Each subsequent attempt doubles it. Default: 1000.

Log Insights

  • Dashboard Name: The OpenSearch index events are written to. The run summary goes to the same name with -Summary appended. Default: iCIMS to Payworks Integration.
  • Select the Analytics Detail Level: Full Details and Custom write one event per record as well as the run summary. Summary Only writes the summary alone. Default: Full Details.
  • Show Attribute Values for Each Event (requires consent to store event data temporarily): Consent to store attribute values alongside each event so the dashboard can show what changed. With consent withheld, the event is still written, carrying its operation and result but no attribute values. Masked fields stay masked either way — see PII & Security.

Attribute Mapper Tab

This tab controls how fields are mapped between the two systems. Each sync direction uses its own, independent map:

  • The Employee map drives the iCIMS to Payworks direction's create and update payloads (the full employee, contact, dates, organization, personal, phone number, sensitive, SIN, tax, and employment containers). This map is required — the integration will not create or update a Payworks employee without it.
  • The Payworks to iCIMS Employee Fields map drives the organization/employment fields written back onto iCIMS People during the Payworks to iCIMS direction's create and update steps. This map is optional; the run still completes without it, simply skipping that write.

Termination is not driven by either map: in both directions, termination writes a fixed value directly (the Payworks payroll status and termination date for iCIMS to Payworks; the configured Termination Status Field Name for Payworks to iCIMS).

How the Integration Processes Records

iCIMS to Payworks

This direction is triggered by an iCIMS WorkFlowStatusChangeEvent webhook, or by a manual candidate run for testing. For each candidate:

  1. The People, Job, and Applicant Workflow profiles are fetched from iCIMS and combined.
  2. The candidate is correlated to Payworks using the Source Correlation Key against the Payworks employee number.
  3. The event is classified as a hire or a termination, based on the configured status categories (or status IDs, which take precedence).
  4. The candidate is bucketed: a hire event with no existing Payworks employee is a Create; a hire event with an existing Payworks employee is an Update; a termination event with an existing Payworks employee is a Delete (termination). Anything else is skipped, with a reason recorded.
  5. The bucketed candidate is checked against its operation's condition and limit.
  6. The operation is executed: Payworks is created or patched, or, for an update, only the fields that actually differ are sent.
  7. On a successful create, the new Payworks employee number is written back to the configured iCIMS field (unless that field already holds a value).

Payworks to iCIMS

This direction is triggered manually for one named iCIMS person, or — when no manual person is set — by polling the full Payworks roster on a schedule. For each target:

  1. The iCIMS person is resolved (directly, for a manual run; by searching on the correlation field, for a roster poll) and the correlated Payworks employee is looked up.
  2. The target is bucketed by the Payworks employee's payroll status and whether iCIMS already holds any mapped value: a terminated employee is a Delete; an active employee with no existing iCIMS values is a Create; an active employee with existing values to diff is an Update.
  3. The bucketed target is checked against its operation's condition and limit.
  4. For Create and Update, the mapped organization/employment fields are written to iCIMS, if changed. For Delete, the configured Termination Status Field Name is set on the iCIMS People profile.

Correlation

Both directions correlate candidates using the same two values: the configured iCIMS field (Source Correlation Key) and the Payworks employee number (Destination Correlation Key). Each direction's keys default to the same fields but are configured independently — if they are ever set to different values, the two directions will stop matching each other's records.

Retries and Idempotency

Transient failures (429, 502, 503, or a timeout) are retried with exponential backoff, up to the configured Transient Retry Attempts. A create is never retried on a timeout, to avoid submitting the same employee twice; the integration instead re-checks whether the employee already exists before giving up.

PII Masking

When Mask Sensitive Fields is enabled, matching values are replaced in every log line, the CSV report, and the notification attachment, showing only the last two characters. This applies regardless of which direction is running.
