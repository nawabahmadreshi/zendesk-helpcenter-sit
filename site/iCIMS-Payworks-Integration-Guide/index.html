iCIMS / Payworks Integration Guide

← Back to index

Overview

This integration synchronizes employees between iCIMS and Payworks, one direction at a time, selected by the Sync Direction setting on the Overview tab. The two directions never run in the same invocation.

iCIMS to Payworks is an event-driven employee lifecycle sync. A candidate whose iCIMS workflow reaches a hire status is created in Payworks; a candidate who already correlates to a Payworks employee is updated instead, with each field skipped when Payworks already matches iCIMS. A termination status sets the Payworks payroll status and termination date. This direction is driven by the iCIMS webhook and processes one candidate per event.

Payworks to iCIMS is a foundational data sync. Payworks organization and employment data is written back onto the matching iCIMS People profile: a Payworks employee with no existing iCIMS values is treated as a first sync and created, one with existing values is diffed and updated, and a terminated Payworks employee instead writes a configured termination-status field onto iCIMS. This direction can be triggered manually for one named person, or run on a schedule that polls the full Payworks roster and correlates each employee back to iCIMS by a configured field.

Each direction has its own independent lifecycle operations, per-operation conditions and limits, and correlation key settings. Candidates are correlated on the configured iCIMS correlation field against the Payworks employeeNumber. Every processed record appears in the CSV report and the notification email with its operation and result.

Key Functions

  • Creates, updates, and terminates Payworks employees from iCIMS hire and termination workflow events, driven by an iCIMS webhook.
  • Writes Payworks organization and employment fields back onto the matching iCIMS People profile, either for one named person or across the full Payworks roster on a schedule.
  • Correlates candidates between the two systems using a configurable iCIMS field matched against the Payworks employee number.
  • Applies independent lifecycle operations (Create, Update, Delete), conditions, and limits for each sync direction.
  • Supports a report-only mode that simulates every operation without writing changes.
  • Supports manual, on-demand runs for a single candidate or a single Payworks-correlated person, for testing.
  • Masks personally identifiable information (social insurance number, birth date, full tax setup) in logs, reports, and notification attachments.
  • Generates a per-record CSV report, run logs, a Log Insights (OpenSearch) dashboard, and success/failure email notifications.

Prerequisites

The following are required before configuring this integration:

  • Tenant Account in the Aquera Admin Portal: You must have a tenant account with admin access in the Aquera Admin portal.
  • iCIMS Application Connector: You must have an iCIMS application connector configured in the Aquera Admin portal, with webhook access for the WorkFlowStatusChangeEvent event type.
  • Payworks Application Connector: You must have a Payworks application connector configured in the Aquera Admin portal.

Integration Setup

This section details the configuration for this integration, organized by tab.

Overview Tab

Applications

This section allows you to select the connectors used for the integration. The following fields are displayed:

  • icims: Select the iCIMS application connector configured in the Aquera Admin portal.
  • payworks: Select the Payworks application connector configured in the Aquera Admin portal.

Parameters

Sync Control Settings

  • Sync Directions: Select which direction runs: iCIMS to Payworks or Payworks to iCIMS. This is a single-select field — only one direction is ever active at once. iCIMS to Payworks creates, updates, and terminates Payworks employees from iCIMS hires, driven by the iCIMS webhook. Payworks to iCIMS writes Payworks organization/employment fields back onto a named iCIMS person's People profile. 

    The employee-number write-back on the iCIMS to Payworks create path is controlled separately by "Write Employee Number Back To iCIMS" (see iCIMS to Payworks Tab).

Operational Features

  • Enable Report-Only Mode: No changes are written to Payworks when enabled. All operations are simulated and the run reports as SIMULATED.
  • Enable Notifications: Send the end-of-run report email and the missing-required-fields alert.
  • Enable Dashboard Generation: Writes one Log Insights event per processed record, plus a run summary, to the OpenSearch dashboard.
  • Enable Logging: Emit progress logging for the run. The configuration table, run summary, warnings, and errors are always logged.
  • Enable Debug Mode: Log full payloads and per-field detail. Note that iCIMS profile data contains personal information — enable only when troubleshooting.
  • Enable Reporting: Write the per-record CSV integration report at the end of the run.

Manual Candidate Run

This section allows you to run the iCIMS to Payworks direction on demand for a single candidate, for testing.

  • Manual Candidate ID: iCIMS person ID to process on demand. When set, the webhook payload is ignored and this one candidate is pulled by API. Leave empty for normal event-driven operation.
  • Manual Job ID: Optional. When empty, it is derived from the People profile's job reference.
  • Manual Applicant Workflow ID: Optional. When empty, it is discovered by search; supply it directly if discovery cannot find it.
  • Manual Run Operation: Select Hire or Terminate. A manual run (Manual Candidate ID set) carries no workflow status, so the operation to exercise is stated outright here.
  • Workflow Person Search Field: Search field relating an applicant workflow to a person, used only when discovering the workflow ID. Default: applicantworkflow.person.id. 

iCIMS to Payworks Tab

This tab configures the iCIMS to Payworks direction: candidate creation, update, and termination driven by the iCIMS webhook.

iCIMS Settings

  • Source Correlation Key: The iCIMS People field holding the Payworks employee number used to match the candidate. This field is also what the reverse direction writes, so it must be writable on the People profile. Configured separately from the Payworks to iCIMS tab's Source Correlation Key — both default to the same field, but if they are ever set to different fields, the two directions will stop matching each other's records. Keep them in sync unless that divergence is deliberate. Default: External ID.
  • Hire Status Categories: Workflow status categories that mean the candidate should be created or updated in Payworks. Matching is case- and whitespace-insensitive.
  • Terminate Status Categories: Workflow status categories that mean the candidate should be terminated in Payworks. Matching is case- and whitespace-insensitive.
  • Hire Status IDs: Optional. When set, these take precedence over the status categories above for classifying an incoming webhook event as a hire.
  • Terminate Status IDs: Optional. When set, these take precedence over the status categories above for classifying an incoming webhook event as a termination.
  • Webhook Event Types: iCIMS event type(s) treated as a genuine hire/terminate webhook. A run whose payload carries none of these, or no payload at all, is treated as having no target for this run (reported as NO_ACTION) rather than a malformed webhook — this integration is event-based only, so an unrelated or empty trigger is never misread as a candidate event and reported as a validation failure.

Payworks Settings

  • Destination Correlation Key: The Payworks employee attribute matched against the source correlation key. employeeNumber is the business key the integration assigns and stores in iCIMS; employeeId is the Payworks-assigned internal key used only in request paths and is never written back. Configured separately from the Payworks to iCIMS tab's Destination Correlation Key — both default to the same value. Default: Employee Number.

Lifecycle Operations

Choose which operations are active for this direction: Create, Update, and/or Delete.

Create Settings

  • Create Condition: Optional JS expression. Variables: SOURCE (iCIMS combined data), TARGET (Payworks employee). Return true to allow the create. Leave empty to allow all hire events.
  • Create Limit: Maximum creates per run. Use "unlimited" for no cap.

Update Settings

  • Update Condition: Optional JS expression. Variables: SOURCE (iCIMS combined data), TARGET (Payworks employee). Return true to allow the update. Leave empty to allow all hire events.
  • Update Limit: Maximum updates per run. Use "unlimited" for no cap.

Delete Settings

  • Delete Condition: Optional JS expression. Variables: SOURCE (iCIMS combined data), TARGET (Payworks employee). Return true to allow the delete/termination. Leave empty to allow all termination events.
  • Delete Limit: Maximum deletes/terminations per run. Use "unlimited" for no cap.

Employee Record Steps

  • Write Employee Number Back To iCIMS: After a create, writes the new Payworks employee number into the iCIMS source correlation field. Without it, the candidate still has no correlation value on the next run, so it would match nothing and be created a second time. Only an empty field is ever filled.

Payworks to iCIMS Tab

This tab configures the Payworks to iCIMS direction: writing Payworks organization and employment data back onto iCIMS People profiles.

iCIMS Settings

  • Source Correlation Key: The iCIMS People field this direction searches/reads to correlate a Payworks employee. Configured separately from the iCIMS to Payworks tab's Source Correlation Key — both default to the same field, but if they are ever set to different fields, the two directions will stop matching each other's records. Keep them in sync unless that divergence is deliberate. Default: External ID.
  • Termination Status Field Name: iCIMS People field to write when a correlated Payworks employee is terminated (payroll status matches the Termination Payroll Status). Tenant-specific custom field name, e.g. field12345. Leave empty to skip the write.

Enable Payworks to iCIMS Lifecycle Management: Master toggle for all Payworks to iCIMS lifecycle operations. When disabled, no iCIMS field is created, updated, or terminated, and every correlated target is reported as skipped.

Payworks Settings

  • Destination Correlation Key: The Payworks employee attribute this direction correlates against. Configured separately from the iCIMS to Payworks tab's Destination Correlation Key — both default to the same value. employeeNumber is the business key stored on iCIMS; employeeId is the Payworks-assigned internal key used only in request paths. Default: Employee Number.
  • Manual Payworks to iCIMS Person ID: iCIMS person ID to process for the Payworks to iCIMS direction. Optional. When left empty, this direction instead polls the full Payworks employee roster (capped by Payworks Roster Max Employees) and correlates each employee back to iCIMS by searching for the configured Source Correlation Key. Their correlation value is looked up in Payworks by employee number, and configured organization/employment fields are written back onto their iCIMS People profile.

Lifecycle Operations

Choose which Payworks to iCIMS operations are active: Create, Update, and/or Delete.

Operation Settings Tab

This tab is organized into four sub-sections: Logging, Reporting, Advance Settings, and Log Insights.

Logging

  • Log Attribute Consent: When disabled, the per-record table is not written to the log at all.
  • Log Detail: Full Details emits every report column. Summary Only emits no per-record rows. Custom applies the attribute list below. Default: Full Details.

Reporting

  • Report Attribute Consent: When disabled, the CSV report is written with no data rows.
  • Report Detail: Full Details emits every report column. Summary Only emits no per-record rows. Custom applies the attribute list below. Default: Full Details.

Advance Settings

PII & Security

  • Mask Sensitive Fields: Masks sensitive values in every log line, the CSV report, and the notification attachment. The forward payload carries the social insurance number, birth date, and the full Canadian tax setup, so this should stay enabled outside of a controlled debugging session.
  • Masked Field Names: Field names masked wherever they appear, matched case-insensitively against both the attribute name and the report column. A masked value is rendered as its last two characters only.

Settings

  • Transient Retry Attempts: How many times a call is retried after a transient failure (429, 502, 503, timeout) before the record is reported as failed. Retries back off exponentially. Set to 0 to disable. Default: 3.
  • Retry Backoff (ms): Base delay before the first retry. Each subsequent attempt doubles it. Default: 1000.

Log Insights

  • Dashboard Name: The OpenSearch index events are written to. The run summary goes to the same name with -Summary appended. Default: iCIMS to Payworks Integration.
  • Select the Analytics Detail Level: Full Details and Custom write one event per record as well as the run summary. Summary Only writes the summary alone. Default: Full Details.
  • Show Attribute Values for Each Event (requires consent to store event data temporarily): Consent to store attribute values alongside each event so the dashboard can show what changed. With consent withheld, the event is still written, carrying its operation and result but no attribute values. Masked fields stay masked either way — see PII & Security.

Notification Tab

Notification Recipients

  • Notification Recipients: Shared recipients for the integration report and the missing-required-fields alert. Used whenever the success or failure list below is left empty.
  • Send On Success: Send the report email for SUCCESS, SIMULATED, and NO_ACTION runs.
  • Send On Failure: Send the report email for FAILED and PARTIAL_SUCCESS runs.

Execution Success Notification

  • Success Recipients: Recipients for successful, simulated, and no-action runs. Falls back to the shared notification emails when empty.
  • Success Email Subject: Leave empty to use the built-in subject.
  • Success Email Body: Leave empty to send the built-in plain-text per-record report. When set, the email becomes an HTML summary card followed by this content.

Execution Failure Notification

  • Failure Recipients: Recipients for failed and partially successful runs, and for the missing-required-fields alert. Falls back to the shared notification emails when empty.
  • Failure Email Subject: Leave empty to use the built-in subject.
  • Failure Email Body: Leave empty to send the built-in plain-text per-record report. When set, the email becomes an HTML summary card followed by this content.

Notification Report Settings

  • Attach Integration Report: Attach the per-record report as a CSV file to the notification email.
  • Notification Report Consent: When disabled, no CSV attachment is added to the email.
  • Notification Report Detail: Full Details emits every report column. Summary Only emits no per-record rows. Custom applies the attribute list below. Default: Full Details.

Attribute Mapper Tab

This tab controls how fields are mapped between the two systems. Each sync direction uses its own, independent map:

  • The Employee map drives the iCIMS to Payworks direction's create and update payloads (the full employee, contact, dates, organization, personal, phone number, sensitive, SIN, tax, and employment containers). This map is required — the integration will not create or update a Payworks employee without it.
  • The Payworks to iCIMS Employee Fields map drives the organization/employment fields written back onto iCIMS People during the Payworks to iCIMS direction's create and update steps. This map is optional; the run still completes without it, simply skipping that write.

Termination is not driven by either map: in both directions, termination writes a fixed value directly (the Payworks payroll status and termination date for iCIMS to Payworks; the configured Termination Status Field Name for Payworks to iCIMS).

Tables Tab

Standard Aquera table functionality is available on this integration for defining custom reference values to use in attribute mapping expressions.

Schedule Tab

Standard Aquera scheduling is available to run this integration automatically on your preferred timeframe.

How the Integration Processes Records

iCIMS to Payworks

This direction is triggered by an iCIMS WorkFlowStatusChangeEvent webhook, or by a manual candidate run for testing. For each candidate:

  1. The People, Job, and Applicant Workflow profiles are fetched from iCIMS and combined.
  2. The candidate is correlated to Payworks using the Source Correlation Key against the Payworks employee number.
  3. The event is classified as a hire or a termination, based on the configured status categories (or status IDs, which take precedence).
  4. The candidate is bucketed: a hire event with no existing Payworks employee is a Create; a hire event with an existing Payworks employee is an Update; a termination event with an existing Payworks employee is a Delete (termination). Anything else is skipped, with a reason recorded.
  5. The bucketed candidate is checked against its operation's condition and limit.
  6. The operation is executed: Payworks is created or patched, or, for an update, only the fields that actually differ are sent.
  7. On a successful create, the new Payworks employee number is written back to the configured iCIMS field (unless that field already holds a value).

Payworks to iCIMS

This direction is triggered manually for one named iCIMS person, or — when no manual person is set — by polling the full Payworks roster on a schedule. For each target:

  1. The iCIMS person is resolved (directly, for a manual run; by searching on the correlation field, for a roster poll) and the correlated Payworks employee is looked up.
  2. The target is bucketed by the Payworks employee's payroll status and whether iCIMS already holds any mapped value: a terminated employee is a Delete; an active employee with no existing iCIMS values is a Create; an active employee with existing values to diff is an Update.
  3. The bucketed target is checked against its operation's condition and limit.
  4. For Create and Update, the mapped organization/employment fields are written to iCIMS, if changed. For Delete, the configured Termination Status Field Name is set on the iCIMS People profile.

Correlation

Both directions correlate candidates using the same two values: the configured iCIMS field (Source Correlation Key) and the Payworks employee number (Destination Correlation Key). Each direction's keys default to the same fields but are configured independently — if they are ever set to different values, the two directions will stop matching each other's records.

Retries and Idempotency

Transient failures (429, 502, 503, or a timeout) are retried with exponential backoff, up to the configured Transient Retry Attempts. A create is never retried on a timeout, to avoid submitting the same employee twice; the integration instead re-checks whether the employee already exists before giving up.

PII Masking

When Mask Sensitive Fields is enabled, matching values are replaced in every log line, the CSV report, and the notification attachment, showing only the last two characters. This applies regardless of which direction is running.
